# backup

Mirror the whole instance to a plain OneDrive folder using `robocopy /MIR`, on demand or on a schedule. The backup is a per-file mirror, not an archive — OneDrive supplies version history and per-file restore.

The target is deliberately a **normal synced folder**, not an encrypted container. A container has to be mounted to be written and dismounted to be synced safely, and WSL holds the mount open; a plain folder has no such conflict, syncs incrementally, and restores one file at a time from the web.

## Usage

```
/backup              mirror now
/backup dry          show what would change; copies nothing
/backup status       last run, verdict, and target
/backup schedule     register (or update) the Windows scheduled task
/backup unschedule   remove the scheduled task
```

## Configuration

Per-install settings live in `^/.state/backup.json`, which `.state/.gitignore` keeps out of git — the path embeds a user profile and tenant, so it must not travel with the codex.

| Key | Purpose |
|---|---|
| `target` | Destination folder inside the OneDrive sync root. Its **parent** must exist. |
| `log` | Robocopy log. Kept outside `^` — a log written into the tree dirties the thing it just mirrored. |
| `history` | One line per run: timestamp, verdict, exit code. |
| `task_name` | Scheduled task name. Also what `/checkWinTasks` looks for. |
| `schedule.time` | `HH:mm` daily run time. |
| `schedule.at_logon` | Add an at-logon trigger as well. |
| `exclude_dirs` | Directories to skip. A bare name (`__pycache__`) matches at any depth; an entry containing a slash (`.state/tests/foo`) is treated as root-relative and matches only that one directory. |
| `exclude_files` | File names or wildcards to skip, at any depth. **This is a security control** — see below. |

A fresh install has no `backup.json`. Create it from the table above before first use; the scripts exit 16 with a pointer if it is missing.

### What is excluded, and why

`.venv`, `.venv.stale`, `.venv.broken`, `__pycache__`, `node_modules` — all regenerable from manifests already in the tree, and non-relocatable anyway (a venv bakes its absolute path into `pyvenv.cfg` and every script in `bin/`). Restoring them would restore something broken.

`/XJ` additionally skips every reparse point. That is not tunable, and is load-bearing:

- the venv `lib64 -> lib` links are unresolvable from Windows and raise `ERROR_CANT_ACCESS_FILE` on every traversal
- `AggregatorM/Delivery` points at a live SharePoint library; following it would pull a separate document set into the backup

Symlinks therefore do **not** survive into the backup. Recreate any that matter after a restore.

### Secrets: `exclude_files` is load-bearing

The target is a cloud-synced folder. Anything mirrored there is uploaded, retained in version history, and recoverable from the recycle bin long after the local copy is deleted. Two categories must never reach it:

- **Credential files** — `.env`, `*.key`, `*.pem`, `*.pfx`, `id_rsa*`, `.netrc`, `.pgpass`, `credentials`. These are gitignored, which means `scrub full` cannot see them (it reads `git ls-files`). Excluding them by name here is the only control that applies.
- **`scrub-*.md`** — scrub reports embed each matched line verbatim (`scrub.py`, `format_report`). A report generated by a path-mode scan therefore *contains* the secrets it found. Mirroring one would leak exactly what the scan was run to prevent.

`.env.example` templates are deliberately **not** excluded — they carry no values and are useful in a restore.

### Deleting an exclusion does not clean the target

`/XF` and `/XD` make a path invisible to robocopy on **both** sides. Adding an exclusion therefore does **not** cause `/MIR` to purge copies already at the destination — they persist as orphans, and `Extras` reports `0`. After adding any exclusion, delete the already-mirrored copies by hand.

For a credential that was mirrored, deletion is still not sufficient: OneDrive retains per-file version history and a two-stage recycle bin. **Treat the credential as disclosed and rotate it.**

## Protocol

The scripts are Windows PowerShell and take Windows paths. From a WSL session, translate the module path first:

1. Resolve the script's Windows path:
   ```bash
   wslpath -w "$CLAUDE_PROJECT_DIR/.codex/explicit/backup/backup.ps1"
   ```
2. Dispatch on the argument:

   | Argument | Command |
   |---|---|
   | *(none)* | `powershell.exe -NoProfile -ExecutionPolicy Bypass -File <backup.ps1>` |
   | `dry` | same, plus `-DryRun` |
   | `schedule` | `powershell.exe ... -File <register-task.ps1>` |
   | `unschedule` | same, plus `-Unregister` |
   | `status` | read the `history` file named in `backup.json`; show the last few lines |

3. Report the summary block and the exit code. Robocopy's codes are already normalised by `backup.ps1` — a non-zero exit means a genuine failure, not merely "files were copied".

## Verifying a backup

Robocopy's own summary reports what it did, not whether the result is correct. To verify the outcome, compare the two trees directly — file counts, byte totals, and any path present on one side only. A live session trace under `.state/traces/` will always differ; that file is being appended to while the mirror runs and is expected to be stale in the backup.

## Interaction with git

`.git` directories are mirrored in full and are the reason this is a plain folder rather than a sync of the working tree: nothing opens those repositories at the destination, so there are no lock files to conflict over and no concurrent writes for OneDrive to tear. Running a sync client over a **live** working tree is what corrupts git, and this command does not do that.

`git push` remains the primary backup for tracked content. This command exists to cover what git ignores — `.state/`, working artifacts, and untracked child projects.

## Related

- `/checkWinTasks <task_name>` — confirm the schedule is still firing
- `/scrub .` — run before first use; the mirror lands in a cloud tenant

  Use **path mode** (`scrub .`), never `scrub full`. `full` reads `git ls-files`, and under this repo's inverted `.gitignore` that is the framework skeleton — a fraction of what the backup carries. Credential files are gitignored and invisible to it. On 2026-07-29 a `full` scan returned PASS while four live `.env` files were mirrored into cloud storage.

  Path mode over the whole tree is slow on a 9p mount (it reads every file in Python). Scoping to the directories that actually change, or pre-filtering with `grep -rIP` using the same patterns, gets the same answer faster.
